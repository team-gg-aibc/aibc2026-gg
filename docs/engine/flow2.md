# 새 흐름(flow2) 한 장

> 새 흐름을 처음 보는 팀원이 이 글만 읽고 실험을 시작할 수 있게 쓴 요약이다(11-11). 측정 기록과 판마다 바꾼 까닭은 [`pm-flow2.md`](pm-flow2.md)(14절)에 있다.
> **`pm-flow2.md`와 이 글의 숫자가 나온 실행 요약(`eval/runs/`)은 결과 PR #77이 병합되면 들어온다.** 그 전에는 브랜치 `donggyu/pm-flow2`에서 볼 수 있다. 아래에서 `pm-flow2.md`라고 적은 곳은 모두 그 문서다.
> 명령의 `python3`은 가상 환경의 파이썬이다(`engine/README.md` 「설치」). 점수는 모두 우리 평가셋의 가중 점수다.

## 1. 무엇이고 왜 보나

- 새 흐름은 PM이 2주기에 따로 실험한 엔진 흐름이다. 지금 흐름(rc-c1)과 단계 순서가 다르다. **3주기(11/11~)부터 팀 실험의 끈 판은 새 흐름 7판이다**(동규 11-11, `docs/decisions.md` 11-11 줄).
- main의 기본값은 그대로 지금 흐름이다. 새 흐름은 설정 파일 `eval/configs/pm-flow2-v7.json`으로만 켜진다.

| | 지금 흐름 (rc-c1) | 새 흐름 7판 |
|---|---|---|
| dev 661문항 가중 (두 번) | 76.6 · 76.3 | **95.9 · 95.4** |
| 극한 283문항 가중 (두 번) | 64.7 · 60.8 | **88.2 · 88.8** |
| 처음 보는 70문항 가중 (두 번) | 88.2 · 80.4 | **95.2 · 98.0** |
| dev 함정 정답률 | 90.5 · 88.1 | 100 · 97.6 |
| dev 과잉 포기 | 19.1 · 19.5% | 2.7 · 2.4% |
| 시간 초과 · 오류 (모든 실행 합) | 0 · 0 | 0 · 0 |
| 답변 시간 중간값 · 95% (dev) | 4.1초 · 7.4초 (11-10 낮) | 5.9초 · 8.7초 (11-10 저녁) |
| 문항당 비용 (기록 기준) | 약 0.14센트 | 약 0.21센트 |

- 두 판의 답변 시간은 잰 시각이 달라 나란히 견줄 수 없다. 업스테이지 API 속도는 시간대에 따라 30~40% 달라진다. 시간은 같은 시각에 나란히 잰 값끼리만 견준다.
- rc-c1 숫자는 11-10에 새 흐름과 같은 날 다시 잰 값이다(릴리스 기록의 76.9와 흔들림 안에서 같다).

## 2. 다섯 단계

질문이 들어오면 먼저 검색(`pipeline.search`, 지금 흐름과 같다)을 하고 아래 다섯 단계를 차례로 돈다. 코드 주석과 측정 문서는 단계를 ① · ③ · ④ · ⑤ · ⑥으로 부른다(②는 없다). 흐름 순서는 `engine/flow2/flow.py` 맨 아래 `STAGES`다.

| 단계 | 하는 일 | 모델 호출 | 코드 | 확인 불가로 끝날 때의 사유 |
|---|---|---|---|---|
| ① 질문 분석 | 답하지 않고 질문을 칸으로만 푼다: 묻는 대상 · 알고 싶은 것 · 유형 · 이름을 든 조례 · 지역 · 묻는 일을 하는 사람 | 1번 | `flow.analyze`, 프롬프트 `a2` | |
| ③ 조례 확정 | **코드만**으로 읽을 조례를 정한다(많아야 둘). 질문이 이름을 든 조례가 6종이 아니거나, 자치구 · 다른 시도가 스스로 정한 것을 물으면 여기서 끝낸다. 검색은 이 단계의 후보 점수에만 쓴다 | 0번 | `flow.route` → `lawmap.route` · `scope_block` · `name_kind`, 지도는 `ontology.json` | 「6종 밖 조례」 · 「관할 밖」 |
| ④ 조례 읽기 · 답 쓰기 | 고른 조례의 **원문 전체**(별표는 표를 줄로 편 글)를 읽고 답 · 결론(네 · 아니요 · 정보) · 근거(조항 이름 + 그 조항에서 옮긴 구절)를 낸다. 결론을 쓰기 전에 질문의 숫자 · 나이 · 자격을 조문 조건에 대어 본 칸(`check`)을 먼저 쓴다 | 1번 | `flow.read` · `view` · `facts`, 프롬프트 `r7`, 별표 `annex.py` | 「found 거짓」 |
| ⑤ 구절 관문 | **코드만.** 근거의 조항 이름이 그 조례에 있고, 옮긴 구절이 그 조항 글에 글자 그대로 있어야 인용으로 남긴다. 없으면 그 인용을 버린다 | 0번 | `flow.gate` · `label_ids` · `quote_in` | 「구절 불일치」 · 「근거 번호 없음」 |
| ⑥ 질문 대조 (마지막 검사) | 질문이 묻는 것을 남은 근거가 정말 정하고 있는지 물음마다 판정한다. 하나라도 「근거 있음」이면 통과다 | 1번 | `flow.check` · `mask_numbers` · `drop_instructions`, 프롬프트 `c8` | 「판정 거절」 |

- 그 밖의 장치: 호출이 10초 안에 안 돌아오면 하나 더 부르고, 깨진 JSON이나 연결 오류는 다시 부른다(`flow.guarded`, 5판). 검색이 끝나면 ①을 기다리지 않고 ④를 미리 부른다(6판, 약 0.9초 줄어듦). 조례가 내용을 상위 법령으로 넘기기만 하는 구절(6종에 네 곳) 뒤에는 코드가 「(※ 그 내용은 이 자료에 없다)」를 붙여 ④ · ⑥에 보여 준다(`flow.DELEG`, 7판).
- 마감(75초) · 오류가 나면 확인 불가 · 출구 검사 · 판단 기록은 `engine/pipeline.py`의 고리를 그대로 쓴다. 출력 네 칸도 같다.
- 2주기에 팀이 확인한 생각 셋이 들어 있다: 질문을 보는 검사(#70) · 조례 통째로 읽기와 조항 이름으로 고르기(#27) · 6종 밖을 코드로 막기(#68).

## 3. 돌려 보기

```bash
python3 -m engine.flow2.flow --selftest                                    # 키 없이 몇 초 (별표 · 조례 확정 · 흐름)
python3 -m engine.flow2.ontology --check                                   # 온톨로지가 원문에서 다시 만든 것과 같은지
python3 -m engine.pipeline "경차 주차요금 할인돼요?" eval/configs/pm-flow2-v7.json   # 한 문항: 응답 네 칸 + 판단 기록
```

판단 기록의 `flow2` 칸에 단계마다 한 일이 남는다: `slots`(① 분석 칸) · `route`(③이 고른 조례와 규칙) · `spec`(미리 읽은 답을 썼는지) · `read`(④의 found · 결론 · 근거) · `gate`(⑤가 남긴 인용과 버린 인용 · 버린 까닭) · `check`(⑥ 판정과 이유) · `guard`(더 부른 호출). 끝까지 잰 실행은 `eval/results/<실행>.html`에서 문항마다 볼 수 있다.

## 4. 재는 법

```bash
python3 eval/run.py --config eval/configs/pm-flow2-v7.json --split dev --repeat 2 --workers 4      # 끈 판. 661문항 두 번: 약 35분, 약 2.8달러
python3 eval/run.py --config eval/configs/pm-flow2-v7.json --split stress --repeat 2 --workers 4   # 극한 283문항 두 번: 약 15분, 약 1.2달러
python3 eval/run.py --config eval/configs/<내 실험>.json --split dev --repeat 2 --workers 4         # 켠 판도 같은 날 · 같은 커밋에서
python3 eval/compare.py <켠 판 실행> --base <끈 판 실행>                                            # 문항별 비교 문서
python3 eval/share.py <실행 이름 …>                                                                # 기록 모으는 곳에 올리기
```

- 끈 판은 `eval/configs/pm-flow2-v7.json`이다. 켠 판은 이 파일을 복사해 `engine` 칸에 자기 스위치만 더한다. 채택 기준과 끝 보고에 붙일 줄은 맡은 이슈와 `docs/engine/plan.md` 5-2절을 따른다.
- **복사한 설정에 `cycle`과 `name`을 적지 않는다.** 주기는 실행한 시각으로 정해지고(`eval/run.py`의 `cycle_of`, 11/11 · 11/12는 3주기), 실행 이름은 설정 파일 이름에서 나온다. 그래서 끈 판 파일에도 두 칸이 없다. 파일 이름을 자기 실험 이름으로 짓고(`<이슈 번호>-<짧은 이름>.json`), `issue`와 `note`만 자기 것으로 고친다. 옛 판 설정(`pm-flow2.json` · `-v2`~`-v6` · `-noonto`)의 `"cycle": 2`는 2주기 기록용이라 그대로 둔다.
- 재는 동안 `engine/` · `eval/run.py` · 설정 파일을 고치거나 커밋하지 않는다. 실행 요약의 커밋 · 엔진 코드 지문은 실행이 끝날 때 찍힌다. 재면서 고치려면 같은 레포의 다른 작업 폴더(worktree)에서 잰다.
- **실행이 끝나면 요약의 `errors` · `timeouts`부터 본다.** 7판은 둘 다 0이 정상이다. `APIConnectionError`가 여러 문항에 이어지면 네트워크가 끊긴 것이니 그 실행은 버리고 다시 잰다. 긴 측정은 컴퓨터가 잠들지 않게 한다(맥은 `caffeinate -i`).
- **처음 보는 문항(`--split fresh`) 실행은 올리지 않는다.** `eval/share.py`가 거부하고, 비교 문서(`eval/compare.py`)와 실패 모아 보기(`eval/failures.py`)도 그 실행을 다루지 않는다. 문항별 결과는 잰 컴퓨터의 `eval/results/`(git에 안 올림)에만 남고, 레포에는 숫자만 든 실행 요약이 남는다.
- 켠 판과 끈 판을 동시에 돌리면 429 오류가 섞일 수 있다(2주기 #68 측정에서 판마다 7~18개). 한 줄씩 차례로 돌린다.

## 5. 스위치와 설정 파일

| 칸 (`engine/config.py`) | 뜻 | 7판의 값 |
|---|---|---|
| `flow` | `"kit"` = 지금 흐름(기본값), `"flow2"` = 새 흐름 | `"flow2"` |
| `flow2_version` | 판 번호(1~7). 판마다 켜지는 동작과 프롬프트 묶음(`prompts.SETS`)이 정해져 있다 | `7` |
| `flow2_hedge_sec` | 호출이 이 초 안에 안 오면 하나 더 부른다. 없으면 끔 | `10` |
| `flow2_ontology` | ③ · ⑥이 온톨로지를 쓰는지(끄면 단순 규칙, 온톨로지 몫을 잴 때) | `true` |
| `flow2_votes` | (PM 실험, 11-11) 같은 호출을 여러 번 나란히 불러 결정(고를 조례 칸 · found와 근거 조항 · ⑥ 판정)만 다수결로 정한다. `{"analyze": 3, "read": 3, "check": 3}` 꼴. 모델이 같은 글에 다른 출력을 내서 같은 문의의 근거가 실행마다 달라지는 것을 줄인다 | 없음(끔) |
| `flow2_memo` | (PM 실험, 11-11) 모델 호출의 출력을 파일에 적어 두고 같은 글에는 그 출력을 쓴다. 같은 문의에는 글자까지 같은 답이 나간다. 값은 파일 경로. **점수를 잴 때는 끈다**(두 번째 실행이 첫 번째의 되풀이가 된다) | 없음(끔) |
| `flow2_handed` | (PM 실험, 11-11 업스테이지 답 1번) ⑥이 거절했어도 답이 「조례에 정해져 있지 않다 + 누가 정하는지」 꼴이고 근거 조항 글에 조례가 스스로 맡기는 구절(「시장이 따로 정한다」 등)이 있으면 그 답을 낸다. 코드만, 호출 수 그대로. `"law"`로 두면 근거 조항이 내용을 다른 법령(「법 제○조」 · 「○○법」 · 6종이 드는 다른 서울시 조례)으로 넘기고 답이 그 법령에서 정한다고 말할 때도 낸다(11-11 업스테이지 2차 답) | `false` |

**실험 스위치를 더하는 법 (3주기부터)**

- **`flow2_version`은 올리지 않는다(7 그대로).** 판 번호는 한 줄로 이어져 있어, 여러 사람이 동시에 8판을 만들면 서로 부딪친다. 채택된 실험을 다음 판 번호로 묶는 일은 배분일에 한다.
- 자기 스위치를 `engine/config.py`의 자기 이슈 절에 더한다. 기본값은 「7판과 같은 동작」으로 둔다. `engine/flow2/` 안에서는 그 스위치로만 가른다(`if cfg["내 스위치"]:`).
- 프롬프트는 고쳐 쓰지 않는다. `prompts.py`에 새 이름으로 더하고(예: `r7`에서 고친 것은 `r8-<이슈 번호>`), 자기 스위치가 켜졌을 때만 그 프롬프트를 쓰게 한다. 판단 기록에 프롬프트 이름이 남아야 한다.
- 스스로 시험(`--selftest`)에 「바뀌어야 할 꼴」과 「바뀌면 안 되는 꼴」을 더한다. 시험 문장은 조례 원문을 보고 새로 쓴다.
- 같은 주기에 같은 함수를 두 사람이 고치지 않는다. 이슈의 「고칠 곳」과 「하지 않을 것」이 경계다.

| 답이 있는데 없다고 한다 | 극한에서 두 번 다 틀린 24문항 중 12 | ④ |

| 옮긴 구절의 글자가 조금 달라 맞는 인용을 버린다 | dev 20 · 25건, 그 탓에 답 전체가 확인 불가가 된 문항 4 · 5 | ⑤ |
| 「이 곳 · 이 구역이 이 조례가 정한 곳인가」를 못 가린다 | 아파트 계단 금연구역 함정(극한 smoking-X023)은 모든 판이 두 번 다 놓친다. 한강공원을 도시공원으로 보고 답한다(시연 장면 점검 4번 중 4번) | ③ · ⑥ |

| 답 글에 「이 자료에 없습니다」 같은 안쪽 말이 샌다 | dev 6 · 5문항 | ④ |
| 지금 흐름보다 느리다 | 중간값 5.9초(지금 흐름 4.1초, 잰 시각이 다름). 모델을 세 번 부른다 | ① · ④ · ⑥ |
| 동시에 여러 문항이 올 때의 시간은 아직 안 쟀다 | 프로세스 전체 동시 호출 상한이 6이다 | 서버 |

이미 해 봐서 다시 하지 않을 것: ④ 프롬프트로 「따져 본 뒤 found를 정하게」 하기(함정은 막지만 답할 수 있는 질문까지 포기), ⑥ 규칙 글을 풀어 주기(거절이 줄어든 만큼 함정이 샌다), ⑥ 빼기(함정이 샌다). 까닭과 숫자는 `pm-flow2.md`(#77 병합 뒤 들어온다) 10 · 12 · 14절에 있다.

## 7. 건드리면 안 되는 것

- **출력 네 칸과 확인 불가 꼴**(`engine/contract.py`). 채점 API 규격이라 칸 하나만 틀려도 0점이다.
- **1~7판의 동작.** 앞 판은 같은 커밋에서 그대로 다시 잴 수 있어야 한다. 그래서 판 번호와 있는 프롬프트를 고치지 않고 스위치 · 새 이름으로 더한다(5절).
- **`engine/pipeline.py`의 고리**(마감 75초 · 오류면 확인 불가 · 출구 검사)와 **`engine/upstage.py`**(업스테이지 호출 한 곳). 고쳐야 하면 이슈에서 먼저 묻는다.
- **`ontology.json`을 손으로 고치지 않는다.** `python3 -m engine.flow2.ontology --build`로 만들고 `--check`로 확인한다.
- **규칙 · 온톨로지 · 프롬프트 예시는 조례 원문에서만 만든다.** 평가 문항의 글이나 낱말을 옮기지 않는다. 엔진 안 모델은 업스테이지 것만 쓰고, 채점 중에는 법령 API를 부르지 않는다.
- **처음 보는 문항(`--split fresh`)과 holdout은 재지도 열지도 않는다.** 고칠 때 보는 세트는 dev와 극한이다. 처음 보는 문항은 판을 고르는 데 되풀이해 쓰지 않고 마지막 후보에만 잰다(`pm-flow2.md` 11절 「조심할 것」). 처음 보는 문항 파일은 레포에 두지 않고 PM 쪽이 배분일에만 잰다(`docs/decisions.md` 11-11).
- 스스로 시험에 고정된 목록(상위 법령으로 넘기는 구절 네 곳 등)을 지우지 않는다.
