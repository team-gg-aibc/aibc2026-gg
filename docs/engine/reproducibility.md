# 실험 재현 규칙

> 네 명이 동시에 실험해도 같은 자로 재고, 다른 사람이 같은 설정을 돌려도 같은 결과가 나오게 하는 규칙이다. 실험을 고르고 채택하는 규칙은 계획 문서 5절(`docs/engine/plan.md`), 결과는 [리더보드](leaderboard.md) · [실험 기록](experiments.md).

## 1. 처음 한 번

```bash
python3 -m venv .venv && .venv/bin/pip install -r engine/requirements.txt
```

- 파이썬 3.10~3.13. 패키지 판은 모두 고정돼 있다(`engine/requirements.txt`). 아래 명령의 `python3`는 이 가상 환경의 파이썬(`.venv/bin/python`)이다.
- 키는 레포 맨 위 `.env`의 `UPSTAGE_API_KEY`에 넣는다(`.env.example` 복사). 키 값은 채팅 · 이슈 · 로그에 쓰지 않는다.
- 내 컴퓨터가 팀과 같은 결과를 내는지 먼저 본다(키 없이, 크레딧 0, 2초):

```bash
python3 eval/run.py --check eval/runs/20261110-021505-start-dev.json
```

「✅ 같은 결과」가 나오면 된다. 「다름」이면 표에서 「다름」인 항목부터 맞춘다(7절). 이 기준 실행은 출발 판을 고정한 `eval/configs/start.json`으로 잰 것이다(11-06 기준 실행 `20261106-201622-baseline-dev`와 문항마다 같은 후보, 11/10부터 이것을 쓴다).

## 2. 실험 하나 = 설정 파일 하나

`eval/configs/<이슈 번호>-<짧은 이름>.json`을 만든다. `engine` 칸에는 끈 판(`engine/config.py`의 `DEFAULTS`, 지금 main의 판)에서 **바꿀 값만** 쓴다.

```json
{"name": "24-top20", "issue": "#24", "cycle": 1, "note": "후보 20개에서 고르기", "engine": {"explore": true, "timeout_sec": 300, "top_k": 20}}
```

- `cycle`은 실험 주기(계획 0절 표, 0 = 출발 판, 1~3 = 탐색, 4~5 = 수렴)다. 리더보드 · 실험 기록이 주기별로 묶는다. 빼면 실행한 날짜로 정한다.
- **탐색 모드(1~3주기)**: `"explore": true, "timeout_sec": 300`을 켠다(바탕 설정 `eval/configs/explore.json`을 복사해 쓰면 된다). 90초를 넘어도 점수에서 빼지 않고 시간은 단계별로 기록만 한다. 문항당 300초가 넘으면 확인 불가로 친다. 리더보드에는 실험 이름 뒤에 「(탐색)」이 붙는다. 수렴 주기(4~5)부터는 두 칸을 빼서 대회 조건(75초에 확인 불가, 90초 넘으면 0점)으로 잰다.

- 실험을 바꾸는 숫자 · 스위치 · 프롬프트 판은 모두 설정 파일에 둔다. 코드에 직접 박은 값은 결과 파일에 남지 않아 나중에 무엇을 바꿨는지 알 수 없다.
- 새 스위치는 `engine/config.py` DEFAULTS의 자기 이슈 절(`# ---- #이슈 …`)에 **지금 동작 그대로(끈 상태)**를 기본값으로 더하고, 설정 파일에서 켠다. 설정 파일에 DEFAULTS에 없는 칸이 있으면 실행이 멈춘다(오타로 조용히 끈 판이 도는 일을 막는다).
- 프롬프트는 고쳐 쓰지 않고 새 판을 더한다(`engine/answer.py`의 `PROMPTS["v2"]` 등). 설정에서 `"answer_prompt": "v2"`로 고른다. 예시 문항(few-shot)은 평가셋에서 가져오지 않는다(점수가 부풀려진다).
- 「끈 판」의 설정 파일은 `eval/configs/baseline.json`이다. DEFAULTS 그대로라 지금 main의 판이다. 배분일에 채택한 실험의 스위치를 DEFAULTS에 켜면 다음 주기의 끈 판이 그 판이 된다(1주기 #22 · #24, 11/10).
- 출발 판(0주기, rc-c0과 같은 동작)은 `eval/configs/start.json`이 고정해 둔다. **DEFAULTS를 바꾸는 PR은 바꾼 칸의 예전 값을 `start.json`에 더한다.** 그래야 1절 재현 점검이 늘 같은 판을 다시 잰다.

## 3. 재는 순서

| 단계 | 명령 | 어림 비용 |
|---|---|---|
| 키 없이 검색만 (조각 · 질문 다듬기 · 묶음은 여기서 먼저) | `python3 eval/run.py --config <설정> --mode retrieval` | 0 |
| 빠른 확인: 켠 판 100문항 | `python3 eval/run.py --config <설정> --sample 100` | 약 $0.05 |
| 빠른 확인: 끈 판 100문항 (같은 날 · 같은 커밋) | `python3 eval/run.py --sample 100` | 약 $0.05 |
| **채택 판단(기본): 켠 판 dev 전체 두 번 이상** | `python3 eval/run.py --config <설정> --split dev --repeat 2` | 한 판 약 $0.38 · 10분 |
| **채택 판단(기본): 끈 판 dev 전체 두 번 이상** (같은 날 · 같은 커밋) | `python3 eval/run.py --split dev --repeat 2` | 한 판 약 $0.38 · 10분 |
| 리더보드 · 실험 기록 다시 만들기 | `python3 eval/board.py` | 0 |

- **재는 법 기본값**: 채택 판단은 dev 전체로 하고, 켠 판 · 끈 판을 각각 두 번 이상 잰다. 100문항 표본은 흔들림이 2.5~4.9점이라 빠른 확인용으로만 쓴다(6절). 표의 비용은 기록 비용(토큰 × 표준 단가)이다. 실제 콘솔 차감은 그 6할쯤이라 dev 전체 한 판이 약 $0.2다(11-06: 기록 비용 합 약 $3.6에 콘솔 차감 $2.14).
- 기본 묶음은 `--split dev`(661문항, 함정 42 포함, 회색지대 40 뺌)다. `kit`(킷 예시 11) · `stress`(극한 283) · `holdout`(10절)도 고를 수 있다.
- **켠 판과 끈 판은 같은 main 커밋 · 같은 문항 · 같은 날**에 잰다. `--sample`과 `--seed`가 같으면 어느 컴퓨터에서나 같은 문항이 뽑힌다(문항 id의 해시 순서, 유형 비율 유지).
- 비용은 2026-11-06 가격표와 문항당 입력 약 2,600자로 어림한 값이다(11-06 실제 콘솔 차감은 이 어림의 절반쯤이었다). **실험 비용 상한은 두지 않는다**(동규 11-06). 크레딧이 모자라면 동규에게 알리고 동규가 대회 측에 추가를 요청한다. 실행마다 비용(`cost_usd`)은 요약에 남는다. 혼자 시험할 때만 원하면 `--max-cost <달러>`로 멈출 수 있다.
- 끝까지 잰 실행은 `eval/results/<실행>.html`(궤적 화면)도 만든다. 문항마다 단계별 입력 · 보낸 프롬프트 · 모델 출력 · 걸린 시간 · 토큰 · 비용이 있고, 원인 · 유형으로 거른다. 리더보드의 「궤적」 칸이 이 파일을 가리킨다(그 실행을 돌린 컴퓨터에서만 열린다). 문항 하나는 `python3 eval/trajectory.py <실행> <문항 id>`로 마크다운으로 본다.
- `--workers`(엔진을 직접 부를 때 기본 4)는 동시에 돌리는 문항 수다. 429(호출 한도)가 나면 줄인다. 지연 숫자는 이 값에 따라 달라지니 견줄 때 같은 값을 쓴다.
- `--url http://…/ask`로 엔진 대신 서버를 부를 수 있다(응답만 받아 틀린 원인은 못 나눈다). 서버가 실제로 쓰는 설정은 결과 파일의 `env.server`(서버 `/health`)로 확인한다. 이때는 대회 채점기와 같게 부른다(11-11 업스테이지 답): 동시에 2문항(`--workers` 기본 2), 접속은 10초 안에 안 되면 오류(다시 시도 없음), 90초는 요청을 보낸 때부터 응답을 다 받을 때까지.

## 4. 결과 파일에 저절로 찍히는 것

실행마다 `eval/runs/<날짜-시각>-<이름>-<묶음>.json`(요약)과 `eval/results/<같은 이름>.jsonl`(문항별 응답 · 판단 기록 · 점수 · 틀린 원인, git에 안 올림)이 생긴다. 판단 기록에는 단계별 시간(`steps`)과 업스테이지 호출마다 단계 이름 · 보낸 메시지 · 모델 출력 · 토큰 · 시간(`calls`)이 들어 있다.

| 무엇 | 요약 파일의 칸 |
|---|---|
| 코드: 커밋, 엔진 코드 지문(`engine/`의 파이썬 파일과 `requirements.txt` 글자의 해시, squash 병합 뒤에도 같음), 채점 코드 지문(`eval/run.py`), 커밋 안 한 수정이 있었나(`engine/` · `eval/run.py` · 설정 파일) | `env.code_commit` · `env.code_hash` · `env.eval_code_hash` · `env.code_dirty` |
| 평가셋: 마지막으로 바뀐 커밋, 실제로 잰 문항의 지문(id · 유형 · 질문 · 정답 조항) | `env.eval_commit` · `env.questions_hash` |
| 설정 전체(모델 이름 · 숫자 · 스위치 · 프롬프트 판), 설정 지문, 끈 판(DEFAULTS)과 다른 칸, 설정 파일 지문 | `settings` · `settings_hash` · `switches` · `experiment` |
| 색인 지문(조각 · 임베딩 파일 해시), 실제로 쓴 검색(hybrid · keyword), 키가 있었나 | `env.index` · `env.retrieval_used` · `env.key_present` |
| 파이썬 · 패키지 판 · 운영체제 | `env.python` · `env.packages` · `env.platform` |
| 날짜(KST) · 걸린 시간 · 호출 수 · 토큰 · 비용 | `created` · `wall_sec` · `calls` · `tokens` · `cost_usd` |
| 실험 이름 · 이슈 · 주기 · 메모 · 설정 파일 | `experiment.name` · `.issue` · `.cycle` · `.note` · `.file` |
| 묶음 · 표본 · 씨앗 · 반복 · 동시 수 | `args` · `group` · `repeat` |
| 점수: 유형별 · 가중 · 함정 · 과잉 포기 · 인용 수 · 지연 · 형식 오류 · 90초 넘음 · 오류 · 검색 적중률 · 조례별 · 틀린 원인별 수 | `metrics` |
| 문항별 검색 후보 지문 · 답 지문(재현 점검이 견주는 값) | `hashes` |

점수 규칙은 킷 채점식이 바탕이다(항까지 1, 조까지 0.5, 별표 인용도 정답, 함정은 「확인 불가」로 시작하는 답 + 빈 인용. 뒤에 「이 내용은 OO법에서 정합니다」 같은 안내가 붙어도 정답). 정답 근거가 여럿이면 근거마다 채점해 평균을 낸다. 11-11에 받은 업스테이지 답대로 두 가지를 더했다(`eval/run.py`의 `score_answer`): 인용 수가 「정답 근거 수 + 2」를 넘으면 넘은 만큼 비례해 깎고(정답 근거 1개에 4개 인용 → 받은 점수의 3/4), 자치구 조례나 규칙 인용이 하나라도 섞이면 그 문항은 0점이다. 조례명 없이 조문 번호만 쓴 인용은 읽히지 않아 0점이다. 같은 날 평가셋 정답 표기도 받은 답대로 고쳤다(`eval/relabel-1111.md`, dev에서 점수에 드는 문항 661 → 693). **그래서 실행 요약에는 점수가 둘 나온다: `metrics.weighted`는 지금 기준이고, `metrics.before`는 같은 응답을 11-11 전 기준(고치기 전 정답 표기 + 킷 채점식)으로 채점한 값이다. 11-11 전에 잰 실행과는 `before`끼리 견준다.** 지난 기록은 `python3 eval/run.py --regrade eval/results/<실행>.jsonl`로 다시 채점한다(모델 호출 없음). 여기에 대회 0점 조건을 더했다: 필드 이름이 네 칸과 다르거나, 답했는데 원문 링크 · 시행일 꼴이 틀리거나, 90초를 넘으면 그 문항은 0점이다. 엔진을 직접 부를 때 75초(`timeout_sec`)를 넘긴 문항은 서버처럼 「확인 불가」로 바꿔 채점한다.

틀린 원인은 판단 기록으로 코드가 붙인다: 정답이 후보에 없음 · 후보에 있는데 잘못 고름 · 판정이 맞는 답을 거절 · 답이 있는데 확인 불가(까닭: 점수 낮음 · found 거짓 · 근거 번호 없음) · 함정에 답함 · 시간 초과 · 오류 · 형식.

## 5. 고정한 것과 흔들리는 것

| 고정했다 | 어떻게 |
|---|---|
| 모델 무작위성 | 온도 0 (`temperature`) |
| 표본 | 문항 id + 씨앗의 해시 순서. 파이썬 판과 상관없이 같다 |
| 같은 점수 후보의 순서 | 조각 번호 순(안정 정렬). 컴퓨터 · numpy 판이 달라도 같다 |
| 패키지 | `engine/requirements.txt`에 모든 판 고정 |
| 색인 | 조각 · 임베딩 파일을 레포에 커밋. 각자 만들지 않는다 |
| 평가셋 · 프롬프트 · 설정 | 커밋 + 지문, 프롬프트는 판 이름 |

| 그래도 흔들린다 | 그래서 |
|---|---|
| Solar 답: 온도 0이어도 같은 질문에 다른 근거를 고를 때가 있다(10/27 킷 예시 M3가 실행마다 0.5 ↔ 1.0) | 출발 판을 같은 100문항으로 3번 돌려 흔들림 폭을 재고, 그 안의 차이는 차이로 보지 않는다(6절) |
| 질문 임베딩: 같은 질문을 세 번 보내면 값이 조금씩 다르다(11-06 실측, 코사인 0.99987) | 혼합 검색 적중률도 실행마다 흔들린다(dev top-6 82.2% · 82.9%, 같은 코드 · 같은 문항). 키워드 검색(키 없이)은 흔들리지 않는다. 검색만 바꾸는 실험도 끝까지 재는 실험처럼 흔들림 폭 안에서 본다 |
| 지연: 네트워크 · 동시 수 · 429 재시도 | 같은 `--workers`로 견주고, 채택 기준은 「지연 95% 지점 30초 안」처럼 넉넉하게 본다 |

`seed`는 업스테이지에 보내지 않는다. 받는지 확인하지 않았고, 모르는 칸을 보내면 400이 날 수 있다.

## 6. 흔들림 폭과 채택 기준

```bash
python3 eval/run.py --sample 100 --repeat 3     # 같은 100문항 3번
python3 eval/run.py --split dev --repeat 3      # dev 전체 3번
```

- 같은 설정을 같은 문항에 3번 돌린다. 가중 점수의 최대 − 최소가 흔들림 폭이다. 리더보드는 같은 문항 표의 출발 판 반복으로 폭을 정하고, 그 표에 반복이 없으면 같은 묶음의 다른 반복 폭을 쓰고 그렇다고 적는다.
- **11-06 실측**: 같은 100문항을 9번 돌리면 가중 62.5~67.4(3번씩 끊으면 폭 2.5 · 3.7 · 4.9점)다. dev 전체 661문항은 같은 코드로 4번 67.1 · 68.2 · 68.1 · 68.1(폭 1.1점)이고, 기록 방식만 다른 앞선 판까지 8번 모으면 66.6~68.2다 100문항 표본은 흔들림이 커서 「폭의 2배」가 10점 가까이 된다. 그래서 **채택 판단은 dev 전체로, 켠 판 · 끈 판을 각각 두 번 이상** 재서 한다(3절 기본값). 100문항은 빠른 확인용이다.
- 리더보드의 「흔들림」 칸: `흔들림 안`(차이가 폭 안) · `↑ 흔들림 밖` · `↓ 흔들림 밖` · `✅ 폭의 2배 넘게 오름`(채택 기준 첫 줄, 계획 5-2절).
- 나머지 채택 기준(2주기부터: 끈 판에서 두 번 다 맞던 함정이 켠 판에서 두 번 다 틀리지 않음 · 과잉 포기가 오류 · 시간 초과를 뺀 값으로 1점 넘게 안 늘어남 · 수렴 주기의 지연 95% 지점 30초 안 · 형식 오류 0, 계획 5-2절)은 리더보드 같은 줄과 r1 · r2 비교 문서로 본다. 함정 · 과잉 포기 줄을 세는 명령은 `docs/work-method.md` 3절 「재는 법」에 있다. 채택 · 버림은 동규가 정한다.

## 7. 재현 점검

```bash
python3 eval/run.py --check eval/runs/<실행>.json
```

- 그 실행과 같은 설정 파일 · 묶음 · 표본 · 씨앗으로 한 번 더 돌려 항목별 「같음 · 다름」 표와 결론을 낸다. 새 결과는 `eval/runs/`에 남기지 않는다.
- 검색만 잰 실행: 문항마다 검색 후보가 모두 같아야 「✅ 같은 결과」다. 키워드로 잰 실행은 키가 있어도 키워드로 다시 잰다(크레딧 0). 혼합 검색으로 잰 실행은 키가 있어야 하고, 질문 임베딩이 실행마다 조금 달라 「다름」이 날 수 있다(5절).
- 끝까지 돌린 실행: 가중 차이가 그 실행의 반복 폭 안이면 「✅ 같은 결과」다(크레딧을 쓴다). 반복 없이 한 번만 잰 실행은 폭을 몰라 「다름」으로 나온다. 먼저 `--repeat 3`으로 재 둔다.
- 「다름」이면: 엔진 코드 지문 → `git pull` · 같은 커밋으로(채점 코드 지문만 다르면 점수 규칙이 바뀌었는지 PR을 본다), 패키지 → `pip install -r engine/requirements.txt` 다시, 색인 → `git pull`(색인 파일이 레포에 있다), 평가셋 → 같은 커밋으로, 설정 파일 → 그때 판으로.

## 8. 기록 남기기 (PR)

1. 남길 실행 요약만 `git add eval/runs/<실행>.json` 한다(켠 판 · 끈 판 · 반복). 시험 삼아 돌린 것은 지운다. 문항별 결과(`eval/results/`)는 git에 올리지 않는다.
2. `python3 eval/board.py` → `docs/engine/leaderboard.md` · `experiments.md`가 바뀐다. 같은 PR에 넣는다.
3. 결론(채택 · 버림 · 보류 + 한 줄 이유)은 그 실행 파일의 `"conclusion"` 칸에 적고 2를 다시 돌린다. 버림 · 보류여도 **배운 점 세 줄**을 `"lesson"` 칸에 목록으로 적는다: ① 무엇이 좋아지고 나빠졌나(종류 · 원인) ② 왜 그런 것 같나 ③ 다음에 해 볼 것. 버림 · 보류 실험의 배운 점은 실험 기록 맨 아래 「배운 점 모음」에 모인다.
   ```json
   "lesson": ["좋아짐 결합 15 · 나빠짐 함정 3(함정에 답함 +3)", "후보가 늘자 비슷한 조항을 함정에서도 골랐다", "함정은 1 · 2위 점수 차로 거르기(#30)"]
   ```
4. **문항별 비교**: `python3 eval/compare.py <켠 판 실행> [--base <끈 판 실행>]` → `docs/engine/compare/<실행>.md`를 같은 PR에 넣는다. 좋아진 · 나빠진 문항, 원인별 문항 수 변화, 나빠진 문항 상위 10개의 단계 요약(정답이 검색 후보에 있었나 · 고른 인용 · 판정)과 배운 점 첫 줄 제안이 있다. 문항별 결과가 있는 컴퓨터(실험한 사람)에서 돌린다. 기준을 안 주면 리더보드의 「기준」 판 가운데 그 컴퓨터에 결과가 있는 것을 쓴다. holdout은 견주지 않는다. 리더보드의 「비교」 링크가 이 문서를 가리켜 GitHub에서 열린다.
5. PR 「검증」에 리더보드 줄과 바뀐 답 예 2~3개를 붙인다. `python3 eval/trajectory.py <실행> <문항 id>`가 그 문항의 단계별 궤적을 마크다운으로 낸다.
6. 두 문서는 손으로 고치지 않는다. PR끼리 충돌하면 main을 받은 뒤 2를 다시 돌린다(같은 실행 파일이면 늘 같은 표가 나온다).
7. **결과만 PR(배분일, 2일마다)**: 버린 실험은 PR을 닫으므로 그 브랜치의 실행 요약이 main에 들어가지 않는다. 그래서 배분일에 오케스트레이터(동규 쪽)가 그 주기의 실행 요약 파일(`eval/runs/*.json`)과 비교 문서(`docs/engine/compare/*.md`)만 모은 「결과만 PR」을 올린다. 결론 칸(채택 · 버림 · 보류 — 한 줄 이유)을 채우고 리더보드 · 실험 기록을 다시 만들어 넣는다. 코드는 넣지 않는다. 모으기 전에 `git fetch origin` 뒤 `python3 eval/board.py --from-branches 'origin/*'`로 병합 전 브랜치까지 한 표로 본다(화면에만 보이고 파일은 쓰지 않는다, 브랜치 칸이 붙는다). 결과만 PR에는 `python3 eval/board.py --tree`로 다시 만든 가설 나무(`docs/engine/tree.json` · `tree.html`, 뿌리 출발 판 → 가설 → 실험 → 다음 가설, 계획 표의 「부모」 칸으로 가지를 그림)도 넣는다. `tree.html`은 데이터를 안에 넣은 한 파일이라 그대로 올려 팀원과 볼 수 있다(holdout · 비밀값 · 연락처는 들어가지 않는다).

## 9. 색인을 바꿀 때 (#23 조각 다듬기 · #28 묶음)

- 키를 넣고 `python3 -m engine.build_index` → `engine/data/`의 조각 · 임베딩 · 짝 지문(`index_paragraph.json`)을 **함께** 커밋한다. 조각만 바꾸고 임베딩을 안 만들면 혼합 검색이 멈춘다.
- 병합되면 다른 사람은 `git pull`만 하면 된다. 색인을 각자 다시 만들지 않는다(임베딩 값이 실행마다 조금씩 달라진다).
- 색인이 바뀌면 그날 출발 판(검색만 + 100문항 × 3)을 다시 잰다. 비교는 같은 색인 지문끼리만 한다.
