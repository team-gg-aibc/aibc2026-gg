# 멘토링 · 멘토링 뒤 회의록 (11/20 금 20:00~)

참석: 동규, 동욱, 종희, 건영

11/20 20:00 마지막 멘토링(현업 멘토)과 그 바로 뒤에 한 회의(24분)를 함께 적었다. 멘토링은 녹음이 없어 동규의 메모로, 회의는 녹음을 받아쓴 글로 썼다. 회의 뒤 PM이 정한 것(11/20 밤 ~ 11/21 새벽)도 「정한 것」에 넣었다. 멘토링 전 회의는 `docs/meetings/2026-11-20-7차-회의록.md`에 있다.

## 정한 것

- 라이브 시연을 목표로 한다. 발표 순서는 그대로 두고, 시연 영상이 있던 자리(4번 장)에 라이브 시연을 넣는다. 전화는 발표자가 대본대로 건다
- 라이브로 갈지는 11/21(토) → 22(일) 넘어가는 밤에 정한다. 기준은 대본대로 했을 때 같은 자리 · 같은 조문이 나오는가다. 아니면 영상으로 한다. 시연할 해피 케이스는 내부에서 10번쯤, 네트워크를 바꿔 가며 시험한다
- 서버는 모두 AWS(시드니)로 옮긴다: 채점용 API 서버 · 글로만 되는 시연용 서버 · 소리까지 되는 발표용 서버. 심사위원과 청중이 한꺼번에 들어오면 집 인터넷 서버로는 못 버틴다. AWS 계정은 동욱 것을 쓴다
- 제출하는 주소는 채점용 API와 시연용 서버 둘이다. 발표용 서버는 내지 않고 라이브 시연에서 우리만 쓴다
- 서버 셋 모두 11/22(일) 제출과 함께 동결한다. 제출 뒤에는 코드 · 서버 · 주소를 고치지 않는다(발표용 포함). 그래서 받아쓰기 · 읽어 주기 작업도 제출 전에 끝나야 한다
- 엔진(채점받는 답변)은 지금 판(채점 서버 판 + 쉬운 말 검사, #135)으로 최종 확정한다. 더 바꾸지 않는다
- 받아쓰기 · 읽어 주기는 일레븐랩스로 한다. 업스테이지 모델에 받아쓰기 · 음성 합성이 없어서다. 위치 좁히기 · 질문 고르기 · 조례 답은 지금처럼 업스테이지 모델만 쓴다. 일레븐랩스는 종희 쪽 계정으로 쓰고 팀 열쇠는 나누지 않는다. 발표에서 「위치 좁히기와 조례 답은 업스테이지 모델, 귀와 입(받아쓰기 · 읽어 주기)만 일레븐랩스」라고 밝힌다
- 통화는 진짜 전화번호(070)를 해 보고, 안 되면 우리만 쓰는 통화 링크와 일레븐랩스만으로 한다. 밖의 사람은 전화로 들어오지 못하게 한다
- 발표에서 한계는 빼고 고도화 방향만 넣는다. 관리 비용 · 효과 수치는 넣지 않는다. 기술은 깊게 들어가지 않되, 「말 한 마디마다 도는 한 바퀴」 흐름은 짧게라도 꼭 넣는다
- Upstage Studio로 바꾸지 않고 지금 그대로 간다
- 동규는 위치 특정을 11/21(토) 12:00까지 닫는다(늦어도 토요일 저녁)
- 발표 자료는 11/22(일) 22:00까지 공유하고, 최종 제출은 동규가 누른다

## 멘토링에서 나온 말 (현업 멘토)

- 아이디어가 매우 좋다는 칭찬을 받았다
- 라이브 시연이 되게 하라. 개인 서버는 대용량 트래픽을 못 버티니 AWS에 올려 시연하는 것이 어떤가
- 받아쓰기 · 읽어 주기(STT · TTS) API를 붙이는 것은 high risk high return
- 위치는 「삼각 기법」처럼 위치 정보 2~3개로 좁혀 간다는 이야기로 끌어가면 좋다
- 강조할 한 문장: 「민원인이 전화를 걸어 민원을 넣을 때, AI가 상담사의 위치 특정을 돕는다」
- 발표는 기술을 깊게 들어가지 말 것. 한계는 미리 말할 까닭이 없다. 향후 방향(고도화)은 넣되 한계는 넣지 말 것
- 사실에 기반한 데이터, 논문 · 모델의 실제 데이터가 있으면 좋다. 설문 · 관리 비용 · 효과를 수치로 넣으면 좋겠다(팀이 모은 설문은 없어 공개 통계로 갈음하고, 비용 · 효과 수치는 넣지 않기로 했다)
- 발표장에서는 네트워크가 중요하다
- Upstage Studio 제품도 들어가면 좋다

## 오간 이야기 (멘토링 뒤 회의)

- 라이브 시연: 잘 되는 경우를 여러 번 시험해야 한다. 고양이 · 상도동 · 강변북로 육교 사이 같은 예시는 이미 위치가 잘 잡히는 것을 봤고, 결국 받아쓰기가 잘 되느냐가 관건이다. LLM은 같은 말에도 다르게 답할 수 있으니, 같은 결과가 나오는 예시 하나를 찾아 대본으로 되풀이하고 발표자가 말하는 연습을 한다
- 책임: 하나하나는 하루 안에 할 수 있지만 나눠서 깊게 해야 하고, PM이 마지막에 다 점검할 시간이 없어 맡은 사람에게 책임이 달린다. high risk다
- AWS: 계정 주인이 크레딧으로 몇 달 열어 둔 적이 있어 일주일은 충분하다
- 발표장 네트워크: 발표장에 유선 랜을 설치할 수 없다고 한다. 우리 노트북을 쓸 수 있으면 휴대폰 핫스팟으로 바꾼다(데이터가 무제한인 팀원이 있다)
- 일레븐랩스: 무료 크레딧은 몇 턴뿐이라 결제가 필요하다. 다른 모델은 모두 업스테이지인데 일레븐랩스만 바깥 모델이라 업스테이지에 물었으나 답이 없었고, 업스테이지에 해당 모델이 없어 밀고 나간다
- Upstage Studio는 거의 쓰지 않았지만 업스테이지 모델(Solar · 임베딩 · Document Parse)은 모두 썼다. 업스테이지 점수는 20점 범위라 깎일 일은 없다고 봤다
- 고도화 방향 아이디어: 조례 6종을 넘어 분야를 넓히면, 분야별 상담센터는 그대로 두고 한 시스템으로 민원을 나눠 줄 수 있다(큰돈 없이 일처리를 효율화하니 고객인 정부에게 좋다) · 신고자에게 접수 내용을 문자로 보내고 신고 링크를 넣기(112의 「접수되었습니다」처럼) · 민원을 넘길 때 바로 정리해 쓰는 인계 서비스
