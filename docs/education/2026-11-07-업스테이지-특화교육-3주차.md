# 11/7 업스테이지 특화교육 3주차 정리

11월 7일(토) 13:00~19:00 기업 특화 교육 3회차(녹화본 5시간 46분)를 팀이 같이 볼 수 있게 정리했다. 온라인 특화교육은 이날이 마지막이고 제출할 숙제는 없다. 강의의 말과 코드는 옮기지 않고 풀어 썼다.

- 이 문서만 읽어도 되게 썼다. 강의는 근로기준법 같은 법률을 예로 들었고 우리 과제(서울시 조례 6종)를 직접 다루지는 않았다.
- 「우리 엔진」은 3주기부터 팀 실험의 바탕인 새 흐름 7판이다(`docs/engine/flow2.md`).

## 한눈에

1. 주제는 **도구 호출(Tool Calling) → 에이전트 → 멀티 에이전트**였다. 모델이 도구를 스스로 골라 부르는 구조가 중심이다.
2. **채점 엔진에는 이 구조를 옮기지 않는다.** 강의의 멀티 에이전트 예제는 한 문항에 1분 41초가 걸렸고 호출 순서가 실행마다 달랐다. 우리는 90초 제한과 네 칸 출력이 먼저라 순서를 코드로 정한다. 강의 교안도 되도록 순서가 정해진 흐름(워크플로)을 쓰라고 권한다.
3. **엔진에 쓸모 있는 것은 강의 시연에서 실제로 난 실패 장면이다.** 우리 함정 문항이 새는 꼴과 같다(3절).
4. **시연 · 발표에는 쓸 것이 많다.** 우리와 가장 닮은 우수 사례(사진 한 장으로 민원 넣기)와, 공공 과제를 보는 기준이 나왔다(4절).
5. 3주기 실험과 이어지는 곳은 3절 표의 마지막 칸에 적었다.

## 1. 하루 흐름

RAG 복습 → 모델 혼자 못 하는 일은 도구로 → 도구를 부르고 결과를 보고 다시 부르는 고리(에이전트) → 법령 API를 도구로 만든 법령 Q&A 에이전트 → 결과를 채점해 보고서로 쓰는 평가 에이전트 → 에이전트를 도구처럼 묶는 멀티 에이전트 → 해커톤 우수 사례.

| 교시 | 다룬 것 |
|---|---|
| 1 | 2주차 RAG를 다시 정리. 필요한 5%에 필요 없는 95%가 섞이면 못 찾는다는 「희석」, 해야 할 것과 하지 말 것의 울타리를 쳐 주는 Harness Engineering |
| 2 | 도구 호출과 에이전트의 개념. 조문을 찾아 주는 도구를 하나 만들어 모델에 붙이기 |
| 3 | 도구를 부를 때 오가는 메시지 네 가지(시스템 · 사람 · 모델의 호출 요청 · 도구 결과)와, 국가법령정보 API를 부르는 검색 도구 만들기 |
| 4 | 도구 세 개로 질문에 답하는 함수를 직접 짜 보고(오류 세 번), 한 줄로 만드는 에이전트로 법령 Q&A를 만들기 |
| 5 | 답을 네 기준(정확성 · 근거성 · 최신성 · 출처)으로 채점하고 보고서를 쓰는 에이전트. 워크플로와 에이전트의 차이. 쟁점 분석 · 근거 검증 · 환각 점검 에이전트를 슈퍼바이저가 부르는 멀티 에이전트 |
| 6 | 해커톤 우수 사례 여섯 개와 주제를 고르는 기준, 질의응답 |

## 2. 꼭 기억할 것

1. **모델은 도구를 직접 실행하지 않는다.** 「어떤 도구를 어떤 값으로 부를지」만 돌려주고, 실행과 결과 전달은 코드가 한다.
2. **도구 호출 요청이 비어 있으면 모델이 혼자 답한 것이다.** 근거를 찾아보지 않은 답일 수 있다.
3. **도구 결과에 없는 말을 답에 덧붙이는 일이 강의 시연에서도 났다.** 조문 한 줄만 받고 다른 내용을 덧붙이거나, 검색 결과가 비었는데 법령 번호를 지어냈다. 「추측하지 마라」는 지시문이 있어도 그랬다.
4. **같은 에이전트가 두 갈래로 갈렸다.** 도구가 「찾지 못했다」고 분명히 돌려준 질문에는 지어내지 않았고, 조문 제목만 돌려준 질문에는 본문이 없다고 쓰고도 아는 지식으로 채웠다. 빈자리는 모델이 알아차리게 두지 말고 코드가 분명히 적어 줘야 한다.
5. **호출 순서를 지시문으로 시켜도 늘 지켜지지는 않는다.** 온도 0인데도 실행마다 답 글과 호출 횟수가 달랐다.
6. **워크플로와 에이전트**: 교안은 되도록 워크플로를 쓰고, 실무에서는 워크플로가 전체를 맡고 그 안의 칸에서만 모델이 판단하게 하라고 권한다.
7. **공공 과제는 「지금 바로 써서 효과가 나는가」를 본다.** 심사위원의 칭찬과 점수는 별개다.

## 3. 우리 엔진에 쓸 것 · 넣지 않을 것

### 쓸 것

| 강의에서 본 것 | 우리 엔진에서 | 지금 상태 · 3주기와 이어지는 곳 |
|---|---|---|
| 빈자리를 분명히 돌려주면 지어내지 않는다(2절 4번) | 조례가 내용을 상위 법령으로 넘기기만 하는 구절에 코드가 「이 자료에 없다」 표시를 붙인다 | **7판에 넣었다.** 그 꼴의 문항 넷이 네 번 실행에서 한 번도 새지 않았다. 다만 11/11에 받은 답으로 이 꼴은 「확인 불가」가 아니라 그 조항을 인용해 안내해야 하는 것으로 정해져, 표시는 두되 답하는 방식은 고쳐야 한다(`docs/engine/scoring-rules.md` 1절) |
| 슈퍼바이저가 조문 하나로 모자라자 벌칙 조항을 다시 찾으러 갔다 | 근거 조항이 가리키는 조 · 항을 코드가 따라가 마지막 검사에 함께 보여 준다. 아파트 계단 금연구역 함정이 이 꼴이다 | 4주기 후보 |
| 평가할 사례를 미리 정해 두고 일부러 틀린 답도 넣는다 | 마지막 검사에 들어가는 입력을 고정해 두고 마지막 검사만 여러 번 불러 흔들림을 잰다 | **3주기에 PM 쪽이 맡는다**(마지막 검사 흔들림: 같은 문의를 다시 넣으면 답이 바뀌는 문제) |
| 검증을 늘 하지 않고 조건이 맞을 때만 한다 | 위험 신호가 있을 때만 마지막 검사를 부른다. 마지막 검사는 답변 시간의 약 40%를 쓴다 | 4주기 후보(위 결과를 본 뒤) |
| 빈 검색 결과에서 번호를 지어냈다 | 답 속 숫자가 근거 원문이나 질문에 글자 그대로 있는지 코드로 본다 | 4주기 후보 |
| 인용문이 원문에 글자 그대로 있는지 보는 도구 | 우리 구절 대조와 같은 생각이다. 강의 코드는 「제○조의2」 같은 가지 조문을 건너뛰지만 우리는 구분한다(대회에서는 가지 조문이 정답일 수 있다) | 이미 하고 있다. 맞는 인용을 버리는 일은 **3주기 예비 「구절 대조 다듬기」**(#84) |

강의 시연에서 난 실패 다섯 가지는 우리 엔진이 막아야 할 목록으로 본다.

| 강의에서 난 실패 | 우리 엔진은 |
|---|---|
| 도구 결과에 없는 말을 덧붙임 | 근거 구절은 글자 대조로 막는다. 답 글에 덧붙인 말을 보는 단계는 아직 없다(위 표의 숫자 대조가 첫걸음) |
| 빈 검색 결과에서 지어냄 | 조례 전체를 읽히고, 근거가 없으면 확인 불가로 끝낸다. 7판 dev 함정 정답률 100 · 97.6 |
| 도구 호출용 제어 글자가 답 글에 새어 나옴 | 새 흐름은 모델에 도구를 묶지 않아 날 일이 거의 없다 |
| 메시지 짝이 안 맞아 오류 응답 | 어떤 오류든 「확인 불가」 네 칸으로 끝난다(#22) |
| 시스템 지시문이 실수로 사라졌는데 그대로 진행 | 프롬프트는 판 이름으로 고정하고 실행 요약에 남긴다 |

### 넣지 않을 것

- **모델이 도구를 스스로 고르는 에이전트 고리와 슈퍼바이저 구조.** 한 문항 1분 41초, 실행마다 다른 순서다. 우리 새 흐름은 중간값 5.9초다.
- **채점 중 법령 API를 실시간으로 부르기.** 대회는 2026-10-01 시행본 고정이다. 지연과 실패만 늘고, 6종 밖 법령이 들어오면 함정에 답하게 된다.
- **되묻는 답.** 강의 평가 사례에는 모호한 질문에 되묻는 답이 정답으로 있었지만, 채점 출력은 네 칸뿐이라 되물을 수 없다.
- **구절 글자 대조를 더 엄하게 해서 함정을 막으려는 시도.** 글자 대조는 구절이 원문에 있는지만 보고 문맥은 못 본다(강의도 같은 한계를 적었다). 함정은 읽기 단계와 마지막 검사에서 막는다.

## 4. 시연 · 발표에 쓸 것

- **우리와 가장 닮은 사례**: 사진 한 장으로 민원을 넣는 서비스(사진 → 위치 · 유형 판단 → 담당 부서 고르기 → 담당자에게 보내기). 해커톤에서 하루 이틀에 만든 작품인데 「바로 쓰겠다」는 평가를 받았다. 심사위원이 이런 사례를 알고 견줄 수 있으니 차이를 한 문장으로 준비한다. 그 서비스는 유형 이름으로만 부서를 골랐고, 우리는 **서울시 조례의 근거 조항 · 원문 링크 · 시행일을 붙이고 근거가 없으면 확인 불가로 가른다.**
- **공공 과제의 기준**: 「이걸 하면 좋다」가 아니라 「지금 바로 써서 효과가 나는가」다. 발표 첫 장의 문제 정의에 넣는다.
- **구조를 설명하는 말**: 「순서와 갈림은 코드가 정하고, 모델은 정해진 칸 안에서만 판단한다」. 교안이 권하는 쪽이라 「왜 에이전트로 안 갔나」는 질문에 그대로 답이 된다.
- **비교 한 장**: 우수 사례들은 「기존 방식의 결과 대 우리 결과」를 나란히 보였다. 우리는 「모델 혼자 답한 것 대 우리 엔진」을 보인다. 견주는 모델도 업스테이지 모델이어야 일관된다.
- **숫자 한 줄**: 사례들은 실제 데이터로 잰 값과 건당 비용을 한 줄로 냈다. 우리도 평가셋 점수 · 함정 정답률 · 문항당 비용 · 답변 시간을 한 벌로 정해 쓴다(동결 판으로 다시 잰 값).
- **평가 네 기준(정확성 · 근거성 · 최신성 · 출처)**: 대회 채점의 근거 정확도 · 신뢰도(원문 링크 · 시행일)와 거의 같은 축이다. 「어떻게 검증했나」 장의 이름을 여기에 맞추면 설명이 쉽다.
- **시연 영상**: 우수 사례의 영상은 1~3분에 사용자 한 사람의 흐름을 따라가며 단계마다 자막 · 내레이션으로 무엇을 하는지 말했다.
- **질의응답**: 칭찬을 받아도 점수가 높다는 뜻이 아니다. 약점(답변 시간, 6종 밖 질문, 틀린 답의 책임, 운영 비용)을 우리가 먼저 말하고 대책을 붙인다.

## 5. 자료 위치

- 교안 두 개(멀티 에이전트 · LangGraph RAG)와 실습 노트북 다섯 개는 강사가 공유한 드라이브의 3주차 폴더에 있다. 받으려면 강사에게 공유를 요청해야 해서 주소는 적지 않았다. 필요하면 동규에게 말한다.
- 실습 노트북을 돌릴 때: 설치 셀은 돌리지 않는다(강사 안내). 업스테이지 키와 법령 API 키가 둘 다 있어야 한다. 강사 코드는 복사하지 않고 생각만 가져온다(`docs/engine/plan.md` 7절).
- 앞선 주차: 1주차는 `docs/education/2026-10-24-업스테이지-특강.md`, 2주차 정리는 디스코드 #자료에 있다.
- 엔진과 이어지는 자세한 점검(강의 내용 32줄을 엔진 단계와 견준 표)은 PM 쪽에 있다. 필요하면 이슈로 옮긴다.

## 6. 낱말 풀이

| 낱말 | 뜻 |
|---|---|
| 도구 호출 (Tool Calling) | 모델이 답을 바로 쓰지 않고 「이 도구를 이 값으로 불러 달라」고 요청하는 것. 실행은 코드가 한다 |
| 에이전트 | 도구를 부르고, 결과를 보고, 더 필요하면 다시 부르기를 모델이 스스로 되풀이하는 구조 |
| 멀티 에이전트 · 슈퍼바이저 | 에이전트 여럿을 도구처럼 감싸 두고, 맨 위 에이전트(슈퍼바이저)가 골라 부르는 구조 |
| 워크플로 | 단계의 순서와 갈림을 코드가 정해 둔 흐름. 우리 엔진이 이쪽이다 |
| Harness Engineering | 모델이 해야 할 것과 하지 말 것의 울타리를 코드로 쳐 주는 일. 우리 엔진의 조례 확정 · 구절 대조 · 출구 검사가 이것이다 |
