# 평가셋 (AI 초안)

우리 엔진이 몇 점인지 미리 재고, 「확인 불가」 기준값을 맞추고, 약점을 찾으려고 만든 문제집이다. 기준값이 너무 낮으면 함정 문항이 0점이 되고, 너무 높으면 멀쩡한 문항이 0점이 된다. 실제 채점은 마감 직후 비공개 문항으로 한 번뿐이라 우리 문제집이 있어야 한다. 10/27 2차 회의 안건 3의 결정대로 **AI가 먼저 만들고 사람이 조례별로 검수**한다. 아직 아무도 검수하지 않았다(`checked_by`가 모두 비어 있다).

문제집은 두 벌이다.

| 묶음 | 파일 | 쓰는 곳 |
|---|---|---|
| **실제 비슷한 세트** | `questions_<키>.json` (867문항) | 점수를 미리 잰다. 난이도를 킷 예시(강사가 만든 문항)에 맞췄다. 개발용(dev)과 마지막 확인용(holdout)으로 나눴다 |
| **극한 세트** | `stress_<키>.json` (230문항) | 점수 예측이 아니라 약점 찾기 · 성능 끌어올리기. 오타 · 계산 · 3단 결합 · 함정 변형 · 프롬프트 인젝션 |

**스타터 킷 원문과 같다.** 킷이 받아 둔 `data/ordinances.json`(기준 20261001)과 견줘 보니 판 번호 6개가 같았고, 조문 · 별표 글자 차이는 공백을 빼고 0이었다. 킷은 주차장 조례의 별도 3~6(주차구획 그림)과 삭제된 제8조 · 제25조의4를 색인하지 않고, 그 밖의 인용 라벨 521개는 모두 이 원문에 있다. 모든 문항의 gold 묶음에는 킷 라벨이 하나 이상 있어서 킷 `check.py`의 `score_citation`으로 바로 채점된다.

## 문항 형식

스타터 킷 `sample_questions.json`과 같은 꼴이다. 안건 3에서 정한 `made_by` · `checked_by`와 아래 칸을 더했다(킷 채점기는 모르는 칸을 무시한다). 칸 순서는 `id, type, question, question_orig, gold, answer_key, note, made_by, checked_by, split, tags`이고, 없는 칸은 건너뛴다.

```json
{
  "id": "parking-S010",
  "type": "단순 조회",
  "question": "모닝 같은 경차를 몰고 서울 공영주차장에 가면 주차비를 얼마나 깎아 줘요?",
  "question_orig": "서울시 공영주차장에서 경차는 주차요금이 얼마나 할인돼요?",
  "gold": [["서울특별시 주차장 설치 및 관리 조례 제7조 제1항"]],
  "answer_key": "「경형자동차」는 주차요금의 100분의 50 할인(지하철 환승주차장에서 환승 목적이면 100분의 80 할인, 1일 1회 최초 3시간 면제)",
  "note": "말투 바꿈",
  "made_by": "ai",
  "checked_by": "",
  "split": "dev"
}
```

- `type`: `단순 조회` · `조건 판단` · `여러 조항 결합` · `근거 없음 (함정)` (킷과 같은 이름)
- `id`: `<키>-S###` 단순 조회, `-C###` 조건 판단, `-M###` 여러 조항 결합, `-G###` 회색지대, `-T###` 함정, `-X###` 극한 세트
- `gold`: 바깥 목록 = 꼭 있어야 하는 근거들, 안쪽 목록 = 「이 중 하나면 정답」. 함정은 `[]`. 조항은 항까지 쓰고, 항이 없는 조는 조까지 쓴다. 별표 문항은 별표와 그 별표를 부르는 조항을 대안으로 함께 둔다.
- `answer_key`: 채점하는 사람이 볼 정답 열쇠다. 「」로 감싼 말은 원문 글자 그대로라서 자동 점검이 gold 원문에서 찾아본다. 조건 판단은 「네」 또는 「아니요」로 시작한다.
- `question_orig`: 말투를 고치기 전 질문(아래 「난이도」). 고친 문항에만 있고, 그때 note 맨 앞에 `말투 바꿈`이 붙는다.
- `split`: 실제 비슷한 세트에만 있다. `dev` 또는 `holdout`(아래 「개발용 · 마지막 확인용」).
- `tags`: 극한 세트에만 있다. 극한 종류 `말투` · `조건 여러 개` · `계산` · `3단 결합` · `항 없는 조` · `별표 계산` · `함정 변형` · `프롬프트 인젝션` 중 하나 이상. `계산`이 붙은 문항은 답이 계산한 값이라 자동 점검이 숫자 대조를 건너뛴다.
- `note`에 쓰는 표시
  - `[사람 확인] 이유`: 문항을 쓴 쪽(AI 또는 사람)이 확신하지 못한 것
  - `[사람 확인: 자동 점검] …`: `check.py --write`가 단 표시. 다시 돌리면 지우고 새로 쓰니 그 뒤에 글을 덧붙이지 않는다
  - `[회색지대] …`: 정답을 아직 정하지 않은 위임 규정형(아래 절)
  - `주의: …`: 함정에서 엔진이 끌려가기 쉬운 비슷한 조항
  - `점검 핵심어: a, b`: 함정에만 쓴다. 6종 원문에 이 말이 있으면 자동 점검이 알린다

## 만든 방법

1. **원문 받기**: `fetch_source.py`가 법제처 국가법령정보 OPEN API에서 6종을 받아 조 · 항(①②…) · 호(1. 1의2. 2. …) · 별표로 나눈다. 나눈 조각을 다시 이어 붙이면 받은 원문과 글자 하나까지 같은지 확인했다(6종 527단위). 응답 안의 상세 링크에 인증키가 그대로 들어 있어서 저장하기 전에 지운다.
2. **문항 만들기**: Claude(Opus 5.5)가 조례 하나씩 맡은 작업 6개로 나눠 동시에 썼다. 업스테이지 API는 쓰지 않았다.
   - 항마다(항이 없는 조는 조마다, 별표는 별표마다) 그 단위 안에 답이 있는 질문을 거꾸로 만든다. 정답 조항(`gold`)은 만들 때 정한 그 단위다.
   - 항 하나짜리 문항은 단순 조회나 조건 판단으로 쓴다. 조건 판단에는 일부러 조건에 안 맞는 경우를 물어 「아니요」 문항을 섞었다(조건 판단 318개 중 113개).
   - 여러 조항 결합은 원칙 + 예외 · 감면 · 절차를 다른 항에서 묶었다. 예: 주차장 제7조 제1항 감면율 + 제3항 「감면 사유가 둘 이상이면 높은 하나만」.
   - 함정은 `common`에 모았다. 주제는 6종과 비슷한데 규정은 다른 데 있는 것들이다(상위 법률 · 자치구 조례 · 다른 시 · 도 조례 · 6종 밖 서울시 조례 · 운영 공고). note의 「실제 규정」에 적은 법률 조항과 조례 이름은 법제처 API로 조문을 직접 찾아 확인했고, 찾지 못한 것은 「확인 필요」라고 적었다.
3. **난이도 맞추기**(동규 10-27 요청): 처음 만든 질문은 조문 낱말을 따라 써서 너무 쉬웠다. 그래서 질문 517개를 시민 말투 · 상황 질문으로 고쳤다(주차요금 → 주차비, 감면 → 깎아 줘요, 「임신한 아내를 태우고 …」처럼). `gold` · `answer_key`는 그대로 두었고, 고치면 답이 달라지는 문항은 고치지 않았다. 고친 질문에는 모두 「서울」을 넣었다. 결합 문항도 70개 더 만들었다(73 → 143). 쉬운 문항은 일부러 3분의 1쯤 남겼다.
4. **극한 세트**(동규 10-27 요청): 조례마다 30~42개, 모두 230개를 따로 만들었다(아래 「극한 세트」).
5. **개발용 · 마지막 확인용 나누기**(동규 10-27 요청): 실제 비슷한 세트를 조례 × 유형마다 80 : 20으로 나눴다(아래 절).
6. **자동 점검**: `check.py`가 아래를 본다. 걸린 문항은 note에 `[사람 확인: 자동 점검]`을 남긴다.
   - 형식(칸 이름 · 순서, 유형 이름, id 중복, split · tags 값), gold 라벨이 원문에 실제로 있는 조 · 항 · 별표인지(자치구 조례 라벨은 여기서 막힌다)
   - 함정이 아닌 문항: answer_key의 숫자와 「」로 감싼 핵심어가 gold 원문에 있는지
   - 함정: note의 `점검 핵심어`가 6종 원문 어디에도 없는지
   - 질문이 조문을 20자 넘게 그대로 옮겼는지, 조건 판단이 「네 / 아니요」로 시작하는지

## 난이도 (키워드 검색으로 잰 값)

킷의 키워드 검색(API 키 없이 글자 2개 단위 BM25)으로 질문마다 상위 6개를 뽑고, 킷 채점식(`score_citation`)으로 정답 근거가 들어 있는지 쟀다. 함정 · 회색지대는 뺀다. 숫자가 낮을수록 어렵다. 기준은 강사가 만든 킷 예시 11문항(함정 2개 빼고 9문항)의 69%다.

| **전체** | 93% (704문항) | **70%** (774문항) |
| 단순 조회 | 98% | 72% |
| 조건 판단 | 92% | 72% |
| 여러 조항 결합 | 77% (73문항) | 63% (143문항) |
| 주차장 | 96% | 71% |
| 도시공원 | 94% | 69% |

## 극한 세트

점수 예측용이 아니다. 엔진이 틀리기 쉬운 문항을 모아 약점을 찾고 고치는 데 쓴다. 실제 비슷한 세트와 섞어서 점수를 내지 않는다. 데이터가 많을수록 평균이 안정되니 조례마다 30~42개를 만들었다.

| 극한 종류(tags) | 문항 수 | 무엇 | 키워드 검색 |
|---|---|---|---|
| `말투` | 60 | 오타 · 줄임말 · 반말(「주차비 얼마임?」 「바베큐존」) | 78% |
| `조건 여러 개` | 50 | 나이 · 시간 · 금액 · 인원 · 감면 겹침 | 92% |
| `계산` | 52 | 별표 금액 · 감면율 · 정족수로 계산해야 답이 나옴 | 92% |
| `3단 결합` | 35 | 원칙 + 예외 + 절차(또는 벌칙 · 위임) 세 곳을 다 찾아야 함 | 73% |
| `항 없는 조` | 36 | 정답이 조까지인 문항(동물보호 제28조, 청년 제3조 등) | 87% |

## 개발용 · 마지막 확인용 (dev · holdout)

같은 문제로 엔진을 계속 고치면 그 문제에만 맞춰진다(과적합). 그래서 실제 비슷한 세트를 조례 × 유형마다 80 : 20으로 나눴다. 묶음마다 id의 해시 순서로 20%를 holdout으로 뽑았다(dev 693 · holdout 174).

**규칙**
1. 엔진(프롬프트 · 검색 설정 · 「확인 불가」 기준값)을 고칠 때는 **dev 점수만** 본다.
2. **holdout 문항의 질문 · 답 · 엔진이 틀린 결과를 보고 엔진을 고치지 않는다.** holdout은 큰 변경을 마칠 때(예: 사전 점검 전 · 최종 제출 전) 한 번 잰다.
3. dev와 holdout 점수 차이가 크면 dev에 맞춰졌다는 신호다. 그때는 holdout을 보고 고치지 말고 dev를 늘린다.
4. 검수(정답 대조 · 말투 고치기)는 holdout도 똑같이 한다. 검수는 엔진을 고치는 일이 아니다. 다만 같은 사람이 엔진도 고친다면 holdout에서 본 내용을 엔진 작업에 쓰지 않는다.
5. 새로 더하는 문항은 `split: "dev"`로 둔다.

## 검수 방법

1. 맡은 파일과 원문 사본(`source/<키>.md`)을 나란히 연다. 원문 사본에서 막히면 위 표의 법제처 링크로 확인한다.
2. 문항마다 아래를 본다.
   - **정답 조항 대조**: `gold`의 조 · 항에 정말 답이 있는지, 더 맞는 항이 따로 있지는 않은지 본다. 단순 조회 · 조건 판단은 표본(5개 중 1개 이상)으로 보고, **전부 볼 것은 빠짐없이** 본다.
   - **말투 바꿈 문항**: `question_orig`와 견줘 뜻이 그대로인지, 고친 질문에도 `gold`와 `answer_key`가 맞는지 본다.
   - **시민 말투로 고치기**: 아직 조문 낱말을 그대로 쓴 질문은 실제로 들을 법한 말로 바꾼다. 처음 고치는 문항이면 원래 질문을 `question_orig`에 남기고 note 맨 앞에 `말투 바꿈`을 붙인다. 정답 조항이 달라지지 않게 고친다.
   - **answer_key**: 원문에 없는 사실이 들어가지 않았는지, 조건 판단의 「네 / 아니요」가 맞는지 본다.
   - 다 본 문항은 `checked_by`에 담당 이름을 쓴다. 해결하지 못한 문제는 note에 `[사람 확인] 이유`로 남기고 PR 「정리」에 적는다.
3. **함정**(D): 6종 어디에도 정말 없는지 본다. `source/*.md` 6개에서 질문의 핵심어를 검색해 보고, 놓친 말이 있으면 `점검 핵심어`에 더한다. 잘못된 함정은 「확인 불가」 기준값을 망치니, 의심스러우면 빼거나 일반 문항으로 바꾼다.
4. **자기 말로 묻는 질문 더하기**: 주변에서 실제로 들은 질문이면 더 좋다. `made_by`에 이름을 쓰고, id는 그 파일의 같은 유형 다음 번호로 잇고, `split: "dev"`로 둔다. 질문에는 「서울」을 넣는다.

## 원문에서 이상해 보인 곳

문항을 쓰다 찾은 것이다. 엔진이 틀리기 쉬운 곳이라 검수할 때 같이 본다.

- **항 번호가 밀린 흔적**: 도시공원 제23조 제5항 「제3항에 따른 과태료」(→ 제4항), 도시공원 제20조 제4항 끝의 「2019년 12월 31일까지 유효」 꼬리표, 금연 제5조 제5항 「제1항제4호부터 제9호」(제4호 · 제8호는 2026.1.5 삭제)
- **인용 번호 어긋남**: 동물보호 제6조 제1항 「제2조제2호」(정의는 제7호), 주차장 별표 3 제목 「(제21제2항 관련)」(「조」 빠짐)
- **오기로 보이는 글자**: 주차장 제18조 제2항 제2호 「1할 계산」, 도시공원 제26조 제2항 「부원장」
- **조 번호가 옮겨 간 조례**: 동물보호는 2025-09-29 개정으로 뒤쪽 조가 2칸 밀렸다(수수료 감면이 옛 제26조 → 제28조, 놀이터 제27조 → 제29조 등). 청년은 2020-03-26에 제19조~제22조가 한 칸씩 밀렸고(→ 제20조~제23조), 2025-01-03에 표창이 제24조에서 제25조로 옮겨 갔다. 옛 판 자료로 답하면 조 번호가 틀린다.
- **법제처 원문의 글자 깨짐**: 별표 일부의 가운뎃점 · 글머리표가 「?」로 온다(주차장 별표 1 비고 4 · 6, 도시공원 별표 2 · 5 · 6). 도시공원 별표 2의 「무료」는 표 줄 때문에 「무 │료」로 쪼개져 있다.
- **숫자에 붙은 호**: 산식의 분모 바로 뒤에 다음 호 번호가 붙어 온다(도시공원 제18조 「…/12」+「2.」 → 「/122.」, 주차장 산식 「/8」+「2.」 → 「/82.」). 그래서 호가 나뉘지 않은 곳이 있다(항 라벨에는 영향 없음).
- 조 끝의 개정 꼬리표(「[전문개정 …]」 등)는 마지막 항 · 호 글 끝에 붙어 온다. 법제처 응답이 그렇다.

## 점수 잴 때

- 엔진을 고치는 동안에는 **dev만** 잰다. holdout은 위 규칙대로 큰 변경을 마칠 때 한 번 잰다.
- 회색지대는 운영진 답이 오기 전까지 빼고 잰다. 답이 오면 그 기준으로 `gold` · `answer_key`를 정하고 `[회색지대]` 표시를 지운다.
- 유형마다 따로 잰 뒤 킷 비율(단순 3 · 조건 3 · 결합 3 · 함정 2)로 가중 평균한다.
- 킷 채점기로 돌리는 법. 파일 여러 개를 하나로 합치면서 split을 고르고 회색지대를 뺀다(마지막 `dev`를 `holdout`으로 바꾸면 holdout).

```bash
python3 -c "import json,glob,sys; s=sys.argv[1]; json.dump([q for f in sorted(glob.glob('eval/questions_*.json')) for q in json.load(open(f)) if q['split']==s and '[회색지대]' not in q['note']], open(f'/tmp/eval_{s}.json','w'), ensure_ascii=False)" dev
```
